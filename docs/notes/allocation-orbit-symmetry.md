# Allocation-tuple symmetry: why ⟨17,17,17⟩ × AE⟨5,5,5⟩ blows up, and how to fix it

## The size of the problem

For target \⟨17,17,17⟩ over the AlphaEvolve \⟨5,5,5⟩=93 outer
template with `maxImbalance=3`, the allocation enumeration is
roughly:

- Per axis: compositions of 17 into 5 positive parts with
  `max - min ≤ 3`. By direct count this is on the order of a few
  hundred to ~1,500 per axis.
- Per (allocA, allocB, allocC): cube the above, so 10⁸ raw before
  symmetry, often 10⁶ after the maxImbalance and maxCombinations
  filters land.

At the current ~200 allocs/s throughput inside `findBestMultiBaseSplit`
that is 1.5+ hours of pure inner-loop work for a SINGLE pool entry.
With 5 pool entries in `PoolConfig.simple`, that's 7+ hours per
shape per round before Phase 2 even fires.

## The symmetry we are not using

A base scheme `B` has an **automorphism group** `Aut(B)` acting on
its three axes plus the three axis-flip generators. For cubic
non-commutative matmul `Aut(B)` always contains:

1. **Axis-permutation** symmetry `S_3` acting on the three axes
   `(A, B, C)` cyclically (via the well-known
   `M → M^T` / `T_{X,Y,Z}` symmetry). For a cubic target this gives
   up to 6× reduction.
2. **Per-axis flip** symmetry generated by `J` (reverse the
   index order on one axis). The axis-flip orbit of `B` has size
   `1`, `2`, `4`, or `8`; reversing `allocA` is equivalent to
   composing the outer scheme with `J^{(A)}`. So if we enumerate
   axis-flip MASKS at the mask layer (which we already do via
   `AnalyticalMaskSearch`), reversing the allocation produces a
   recombined scheme that is the SAME as some
   `(allocA, …)` under a different mask.

Composed: an allocation tuple
`((a_1, …, a_{n_o}), (b_1, …, b_{m_o}), (c_1, …, c_{p_o}))` is
equivalent to any image under the group generated by:

- **Cyclic axis rotation** `(allocA, allocB, allocC) → (allocC, allocA, allocB)`
  when the base is fully cubic-symmetric. For cubic-target `n=m=p` we
  enumerate three permutations and would converge to one canonical
  member per cyclic orbit.
- **Per-axis reversal** `allocA → rev(allocA)` modulo the
  mask-layer covering: reversing `allocA` IS the same as keeping
  `allocA` and flipping axis-A of the outer scheme. If we enumerate
  all 8 axis-flip masks, the alloc-reversal is already covered.

The combined reduction is roughly:

```
  cubic-symmetric S_3 :  ≤ 6×
  per-axis reversal × 3 :  ≤ 2³ = 8×   (modulo mask coverage)
                          ----
  total                :  ≤ 48×
```

Realistic reduction is somewhere between 8× (mask-only) and 48× (mask
+ axis-permutation).

## Canonical form for allocation tuples

A natural canonical form, applicable when the base is fully
cubic-symmetric and we enumerate all 8 axis-flip masks:

1. Reverse each per-axis allocation to its lex-min form
   (`min(alloc, rev(alloc))` by tuple comparison). This commits to
   one representative per axis-reversal orbit. Cost: O(3 dim).
2. For cubic targets `n = m = p`, sort `(allocA, allocB, allocC)`
   lexicographically as a triple. This commits to one representative
   per axis-permutation orbit. Cost: O(3 dim log 3).

The canonical-form check is `O(dim)` per allocation. Skipping
non-canonical allocations saves the full
`Recombination.recombineWithAllocation` call (the expensive bit).

**Important caveat.** The cubic-symmetric step (2) assumes the base
has full `S_3` automorphism on its axes. For Strassen and Winograd
\⟨2,2,2⟩ this is true (Burichenko stabilizer order 36). For
AlphaEvolve \⟨5,5,5⟩=93 we have not verified. The safe default is:

- always apply (1) (axis-reversal canonicalisation),
- gate (2) on a base attribute `cubicSymmetric: true` that we set
  explicitly per pool entry.

The current pool's `Recombination.recombineWithAllocation` does NOT
exploit either reduction. The 1.5-hour AE\⟨5,5,5⟩ inner loop at
⟨17,17,17⟩ is the cost of not exploiting it.

## Implementation sketch

Inside `findBestMultiBaseSplit`, before the
`recombineWithAllocation` call:

```java
// (1) axis-reversal canonicalisation. Already covered by mask
//     enumeration, so a non-canonical reversal alloc is a duplicate.
if (compareLex(aA, reversed(aA)) > 0) continue;
if (compareLex(aB, reversed(aB)) > 0) continue;
if (compareLex(aC, reversed(aC)) > 0) continue;

// (2) axis-permutation canonicalisation, when cubic.
if (n == m && m == p && nb.cubicSymmetric()) {
    // Sort the three allocations lex-wise; skip if not the
    // canonical (smallest) member of the cyclic orbit.
    int[][] sorted = sortLex(new int[][] {aA, aB, aC});
    if (!java.util.Arrays.deepEquals(sorted, new int[][] {aA, aB, aC})) continue;
}
```

Expected speedup at ⟨17,17,17⟩ × Strassen / Winograd (the safe set):
- step (1) alone: ~8× (rough).
- steps (1)+(2): ~24-48× (rough, depends on palindromic / fixed-point
  allocations that don't reduce).

For AE\⟨5,5,5⟩=93 the speedup applies ONLY after one of the
mask-coverage fixes above lands. The 22-min observed CPU for this
base is NOT closed by a one-line lex-min check.

## Risks

1. **Mask-coverage assumption — load-bearing.** Step (1) is only
   safe if the axis-flip orbit of the base IS covered, either by
   mask-layer enumeration (`AnalyticalMaskSearch`, 2x2x2 only
   today) OR by separate pool entries for each orbit member. The
   simple-pool entry `AE<5,5,5>=93` is tagged `CANONICAL`
   (orbit mode = CANONICAL, see `PoolConfig.simple()`), which means
   the axis-flip orbit is **NOT** expanded into the pool. So for
   `AE<5,5,5>=93` step (1) would lose coverage as-is — the
   speedup is real only after one of:
   - extending `AnalyticalMaskSearch` to non-2x2x2 bases, OR
   - flipping the pool's orbit mode away from CANONICAL for the
     AE entry, OR
   - per-base axis-flip-coverage audit + flag.

   For Strassen-cubic and Winograd-cubic entries the orbit IS
   covered by `AnalyticalMaskSearch`; step (1) is immediately
   safe there. The bottleneck base for our \⟨17,17,17⟩ closure
   is **not** in the safe set.

2. **Cubic-symmetry assumption.** Step (2) requires the outer
   scheme to be invariant under cyclic axis-permutation. For
   AlphaEvolve and Smirnov templates, this may not hold. Gate
   strictly on a per-pool-entry attribute; do not assume.

3. **Lineage record.** A win discovered under the canonical alloc
   needs a lineage record that captures which symmetry transform
   was applied so `LineageReplayer` can re-construct. Should
   reuse the existing `AxisFlip` / `AxisPermute` lineage nodes.

## Status

**Implemented (task #131)**: step (1) per-axis reverse canonicalisation
in `BlockSplitSearch.findBestMultiBaseSplit`, gated on
`base.n == 2 && base.m == 2 && base.p == 2 && peel == null` so the
mask sweep below covers the orbit. Helper `lexGreaterThanReverse`
in the same file.

For Strassen / Winograd 2×2×2 outers at ⟨17,17,17⟩ with imbalance=3,
this drops per-axis alloc count from 4 to 2 (keeping `(7,10)`,
`(8,9)`; skipping `(9,8)`, `(10,7)`) → 8× fewer (allocA, allocB,
allocC) triples evaluated. Measured: Strassen-only probe runs in
~0.6s, finding rank 2940 (worse than catalog's 2931, which is
correct — Strassen alone doesn't close the (9,8)³ gap; needs Winograd
+ analytical mask sweep + sub-product depth).

A tried-and-reverted experiment lifted the 2×2×2 gate on the mask
sweep so step (1) could apply to AE-5×5×5 too; for r=93 outer
schemes the 8-mask scoring per allocation dominated the savings and
made the search slower overall. The cached-supports refactor
(`SchemeSupports` reused across the alloc loop instead of
re-extracting per call) remains in place — it's a no-cost win for
2×2×2 and a non-cost change for larger bases.

## Next steps (still open)

- **Smarter mask scoring** that early-exits when mask=0 is provably
  optimal. Would let us re-enable mask-coverage for non-2×2×2
  bases without paying the 8-mask cost per alloc.
- **Pool axis-flip expansion** for selected non-2×2×2 entries
  (e.g.\ AE-5×5×5): switch `PoolConfig.simple()` to expand the
  orbit for high-r entries. Cost: 8× larger pool for those entries;
  benefit: step (1) becomes safe for them.
- **Step (2) cyclic axis-permutation** for cubic-symmetric bases on
  cubic targets. Need a per-base `cubicSymmetric` attribute. Up to
  6× more reduction on top of step (1) for the cubic case.
